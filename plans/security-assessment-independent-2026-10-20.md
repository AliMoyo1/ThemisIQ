# ThemisIQ security assessment: independent review and combined remediation

Date: 2026-10-20. Scope: repository code and checked-in deployment configuration only.

## Baseline and confidence

The current workspace was on `claude/plan-04-platform-truth` at `2908a5b70b271905da9356960439f5a12e7032f8` when reviewed. It had numerous pre-existing, uncommitted changes, including AI literacy removal and work in other modules. This report did not change product code. The earlier assessment is in `.claude/worktrees/status-after-pr11/plans/security-assessment-2026-10-20.md`, on a different worktree at `27f04cf9fbb46d3cad1b51c17caf4c33efce636d`. The two baselines must not be conflated with the deployed release.

I independently traced authentication, MFA, authorization, tenant and business-unit scoping, the public integration API, Vault upload and download paths, report access, external-form import, client-side rendering, AI calls, outbound HTTP policy, and the checked-in service and nginx configurations. I inspected tracked database files without printing their records. I did not run the test suite, conduct a dependency vulnerability scan, exploit the live application, or inspect the VPS, DNS, firewall, Cloudflare, mail account, or production database. Code-confirmed means a defect or risky path is present in this checkout; it does not establish that the same revision is live. The earlier report's browser proofs apply to its own worktree, not automatically to this one.

This is a prioritized assessment, not a claim that all 1,000-plus routes and every browser sink were manually proved safe. Prior findings that remain in the current code are grouped below. **High** means plausible material confidentiality, integrity, or availability impact. **Medium** means a narrower or conditional impact. **Low** means hygiene or an item that needs a policy decision.

## Detailed findings and fixes

### 1. ARIA document-list stored XSS, P0, retained from H1

`oneforall/modules/aria/routes.py:54` replaces Jinja's `tojson` with `Markup(json.dumps(...))`. `oneforall/modules/aria/templates/documents.html:173` puts a document object into a single-quoted `onclick` attribute. A document field containing a quote can break the attribute boundary. The earlier assessment recorded a browser proof with a crafted title. The current checkout still has both lines. The permissive inline-script CSP in `oneforall/core/middleware.py` makes the injected event handler executable.

**Fix:** remove the override, use Jinja's built-in `tojson` for script data, and replace the inline `onclick` with `data-doc-id` plus `addEventListener`. Keep all database text out of executable attributes. Test the rendered DOM with a title containing single and double quotes, HTML entities, and a script closing sequence. [Jinja documents the context rules for `tojson`](https://jinja.palletsprojects.com/en/stable/templates/); [OWASP recommends fixed handlers over untrusted event-handler attributes](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html).

### 2. ERM appetite-card stored XSS, P0, new

`oneforall/modules/erm/routes.py:941-951` accepts an appetite body for users with `erm.appetite.manage`, granted to Risk Owners and Super Admins at `oneforall/core/rbac.py:260`. `oneforall/modules/erm/data_service.py:1921-1968` stores `category` without restricting it to a trusted taxonomy key. The readable `/erm/api/appetite/status` returns that stored value. `oneforall/modules/erm/templates/index.html:2214` inserts `a.category` directly into JavaScript inside an inline `onclick`. Line 2215 calls `esc(a.category)` in a second inline handler, but HTML entity decoding happens before the browser interprets that JavaScript, so HTML escaping alone is not a safe boundary. Every viewer of the appetite card can encounter the stored handler. This was traced in source, not browser-exploited during this review.

**Fix:** render a numeric appetite ID as data, attach delegated listeners, look up the category in the response object, and pass it as a function argument. Validate category membership or a documented custom-category policy server-side. Remove the two inline handlers. Test an authorized Risk Owner storing a quote-bearing category and opening the card as another role; no new DOM handler or script execution should occur. Search the remaining ERM inline handlers for the same pattern, especially any user-controlled category or label.

### 3. MFA tenant policy and enrollment, P0, retained from H2/H3

`oneforall/modules/launcher/routes_auth.py:131` calls `get_setting("security.require_mfa")` after password authentication but before tenant context is bound. `oneforall/database.py:509-526` reads the current context when opening PostgreSQL connections, so a non-default tenant's setting is not selected at this point. The login route then creates an MFA-pending session for an unenrolled person, but `oneforall/core/middleware.py:33,55-61,77-83` allows that pending session to visit verification, not setup. The earlier assessment browser-proved the lockout. The forced-password-change redirect is a second gate to account for during the repair.

**Fix:** return the trusted organization identifier with the authenticated user, bind that tenant while fetching its MFA setting, and clear the context on exit. Implement a constrained enrollment state: the pending, unenrolled session may access setup and enable, cannot reach app routes, and is promoted only after a valid first code. Do not regenerate the pending secret on every setup-page refresh. Decide and test the order when both a password change and MFA enrollment are required. Use two PostgreSQL tenants with opposite policies and a full login-to-enrollment browser flow as release criteria.

### 4. Task AI scope and provider disclosure, P1, retained from M2 with correction

`oneforall/modules/launcher/routes_platform.py:955-1000` lets any authenticated user submit the latest 30 open tasks to the AI provider, including titles and description excerpts, and returns the model's ranked IDs without a visibility check. The task-list route at lines 649 onward applies tenant and business-unit scope. **Correction to the earlier report:** the list is not limited to creator or assignee; the right fix is to use its visible-scope contract, then decide as a product policy whether prioritization should narrow to the user's own tasks. Merely adding a creator/assignee filter would silently change the feature's intended scope. The provider transfer also needs the current organization's AI policy and data-category decision.

**Fix:** centralize the task visibility predicate, use it for list/detail/prioritization, minimize fields sent, and accept model output only for IDs in the already-authorized input set. Add per-user and per-org budgets. A scoped two-business-unit case must show that a wrong-unit task never appears in the provider payload or response.

### 5. Blocking work on the single ASGI worker, P1, new

`oneforall/scripts/systemd/themisiq-app.service:20` starts one Uvicorn worker, intentionally because schedulers run in process. The `async` task-prioritization route calls the synchronous `core.ai_client.create_message` (`oneforall/core/ai_client.py:307`), whose HTTP provider calls use `httpx.Client(timeout=120)`. The `async` Vault PDF route at `oneforall/modules/evidence/routes.py:1118` calls `subprocess.run(..., timeout=60)` for LibreOffice at line 1209 and then loads the resulting PDF fully into memory. These calls block the event loop while they run. An authorized request to a slow provider or a costly document conversion can therefore delay unrelated requests on the only worker. The magnitude in production has not been measured; this is a code-path availability risk, not proof of a production outage.

**Fix:** use an async HTTP client or run synchronous provider calls in a bounded worker pool; move PDF conversion to a separate constrained worker/process with limits on input, output, runtime, memory, and concurrency. Serve the result from a temporary file when appropriate. Keep schedulers single-instance independently of web worker count before adding workers. Acceptance should include a slow-provider and slow-conversion exercise where `/health`, login, and another user's request remain responsive and the queue rejects excess work predictably.

### 6. API-key privilege and audit, P1, expanded from L8

`oneforall/modules/launcher/routes_api_v1.py:41-85` authenticates a key with only `read` or `write` scope and binds its tenant. The read key can list all tenant risks, GRID audits and Sentinel breaches (`:137-242`) without a business-unit predicate. The write key can create or patch cross-module risks, including `status`, `owner_id`, and source identifiers (`:243-305`), with no per-operation `log_audit` call. The generic mutation audit middleware covers `/sentinel`, `/bcm`, `/erm`, and `/orm` paths, not `/api/v1`. Key creation at `oneforall/modules/launcher/routes_admin.py:1049-1081` accepts scope and expiry fields without constraining them to a resource set or requiring a finite expiry. These keys are issued by Super Admin, so this is **not** an unauthenticated cross-tenant access finding. It is a least-privilege and traceability gap, especially if a read key is shared with an integration that should never receive breach descriptions.

**Fix:** make key grants explicit, for example `risks.read`, `audits.read`, `breaches.read`, `risks.create`, and `risks.update`, each with tenant and optional unit scope. Record key ID, integration name, operation, entity ID, result, and source IP in an immutable audit trail. Enforce field-level validation and allowed transitions for writes, rather than trusting a broad `write` label. Require finite expiry and support rotation. Test wrong-unit reads, forbidden fields, revoked/expired keys, and audit records. The generated capability inventory currently labels `/api/v1/*` as `public` because it misses FastAPI dependencies; that documentation should be corrected, but the routes do require API keys.

### 7. Vault hidden-file existence signal, P2, new

`oneforall/modules/evidence/routes.py:635-653` first looks for a visible duplicate, then queries the caller's whole organization for the same SHA-256. If a file exists only in another unit, it responds `409` with `duplicate: true` and `hidden: true`. `oneforall/tests/test_evidence_proof.py:322-331` explicitly expects that response. This does not reveal the title or ID and requires possession of the exact file bytes, so its reach is narrower than a listing leak. It nevertheless confirms existence across unit boundaries and conflicts with PLAN-37's no-existence-signal standard. The test is evidence of intentional current behavior, not proof that the standard was changed.

**Fix:** decide whether organization-wide deduplication is permitted to disclose a hidden match. If not, deduplicate internally without distinguishing hidden from absent records to the caller, and route any sharing request to a privileged custodian without revealing the match. Keep visible duplicate handling separate. Test response and timing equivalence for absent and hidden identical files, plus concurrent uploads and storage cleanup.

### 8. Sessions and MFA secrets, P1/P2, retained from M1/M8

Self password changes and admin resets update password hashes without clearing live sessions (`oneforall/modules/launcher/routes_auth.py:394-435`, `oneforall/modules/launcher/routes_admin.py:532-560`). MFA changes likewise need session invalidation and rotation. `oneforall/core/auth.py:35-60` stores **SHA-256 hashes** of session tokens, so the earlier report's suggested comparison against a raw cookie in `DELETE ... token <> %s` would be wrong. Use the hashed token or session row ID, and make revocation part of the same transaction as the credential change where feasible. Existing expiry limits exposure but do not replace incident response.

`oneforall/core/mfa.py:170-190` accepts a valid TOTP again within its window, and the TOTP secret is stored in plaintext. Record the last accepted time step with an atomic compare-and-set so concurrent submissions cannot reuse it; encrypt the secret with a separate deployment key and plan key rotation and backup recovery. Backup codes already use a compare-and-set, which is a useful pattern to reuse. [OWASP session guidance](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) supports active invalidation after credential changes.

### 9. AI authorization, cost, and prompt integrity, P2, retained from M3/M4/M5

`oneforall/core/ai_policy.py:268-286` permits an AI call if the organization has no saved policy or no organization context. The text wrapper in `oneforall/core/ai_client.py:884` uses fixed `<user_input>` tags and does not neutralize a closing tag in imported or retrieved material. Some callers interpolate stored text without that wrapper. `oneforall/static/js/ai-guidance-dialog.js:7-10` claims that wrapping means guidance "can never override" system rules; that assurance is too strong. Treat this as an output-integrity and potential disclosure risk, not as proof that the model can execute unapproved actions. The earlier report grouped report narratives with these call sites, but that particular narrative uses aggregate statistics, so it should not be ranked as if it ingested an arbitrary external document. The governance drift summary writes model-generated prose, while deterministic task creation is separate, so its immediate risk is misleading retained content rather than model-controlled task execution.

**Fix:** require an explicit effective policy before tenant data leaves the platform, bind organization context in scheduled jobs, and set conservative default data categories and budgets. Enforce quotas in the shared AI client with atomic accounting, not only route decorators. Treat all retrieved and imported text as untrusted data. A stronger delimiter is a layer, not an authorization boundary; validate IDs, links, facts, and side effects outside the model, with human review for consequential writes. Update the UI copy to describe guidance as untrusted. [OWASP prompt-injection guidance](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html) makes the same distinction.

### 10. External and operational controls, P1/P2, retained from M6/M7 and selected lows

The checked-in nginx site (`oneforall/scripts/nginx/themisiq:29-30`) names `app.themisiq.net` and `monitor.themisiq.net` in the same port-80 block, and its catch-all proxies to the whole app. The comments say the monitor is direct HTTP. **Live DNS, Cloudflare, firewall, and installed nginx config were not checked**, so production exposure must be verified. The origin middleware would reject many cross-origin POSTs but cannot retroactively protect credentials sent over cleartext. Give the monitor its own health-only HTTPS endpoint or private uptime probe and restrict direct origin traffic. Review the bridge webhook route on the same host before changing it.

The CSP in `oneforall/core/middleware.py:431-449` retains `unsafe-inline`, which weakens protection against the two XSS paths. Move inline handlers out of templates, then migrate inline scripts and styles to nonces/hashes or static assets and tighten CSP in report-only mode first. Do not present CSP as a substitute for fixing unsafe sinks.

The earlier report's remaining low findings are still relevant but should be handled as hardening and configuration decisions: public OpenAPI schema; demo-request abuse limits; IP-only, fail-open login throttling; password strength; file-type allowlist and sandboxing; missing explicit `defusedxml` dependency; stale session cleanup; obsolete `X-XSS-Protection`; and whether people-directory/inventory visibility is deliberately organization-wide. `git ls-files` shows **two** tracked SQLite paths: `data/oneforall.db` (about 1.09 MB, four user rows and one hashed session row) and `oneforall/oneforall.db` (empty). Remove both from future tracking after checking deployment reliance; assess Git history before assuming old data was harmless. No raw database contents were printed. The broad `psycopg2-binary>=2.9.9` requirement also means the dependency set is not fully reproducible despite the comment in `requirements.txt`. Do not assert that packages are CVE-free without a successful advisory check.

There is also an upload-boundary mismatch to resolve as a reliability and denial-of-service control: `oneforall/core/middleware.py:573-588` rejects declared request bodies above 5 MB, while `oneforall/modules/evidence/routes.py:130,560-580` advertises and reads up to 100 MB for a Vault file. The middleware checks only `Content-Length`; it does not itself count streamed bytes. Confirm the effective nginx `client_max_body_size`, multipart parser behavior and intended Vault limit, then enforce one coherent limit on the actual byte stream. No bypass or successful large upload was attempted in this review.

## Release-oriented remediation sequence

1. **Contain executable-content paths.** Patch ARIA and ERM inline-handler XSS. Review adjacent inline handlers with stored text. Add a strict CSP rollout plan. If the current deployed release contains these paths, prioritize a short security release rather than waiting for the larger UI build.
2. **Make sign-in policy reliable.** Fix tenant-bound MFA reads and the enrollment state machine together. Add session revocation on password reset/change and MFA changes. Exercise two real PostgreSQL tenant schemas before rollout.
3. **Close data-flow gaps.** Scope task AI input and output; design integration-key grants and audit; settle the Vault hidden-duplicate policy. Use negative cases with wrong-unit users and integration keys.
4. **Protect availability and AI boundaries.** Remove blocking work from the single web event loop, bound background work and output size, enforce effective AI policy and atomic budgets, and validate model output near each use.
5. **Verify production controls separately.** Compare installed nginx config and DNS/firewall to the repo, check backup and rollback readiness, perform a dependency advisory scan with valid TLS, review sender and secret configuration, and run focused browser/real-PostgreSQL security checks before release. None of those live-state checks is claimed complete by this report.

## Positive controls observed, with limits

The inspected code stores session **hashes**, not raw tokens; module report opens use snapshot integrity and recipient-scope checks (`oneforall/modules/launcher/routes_reports.py:303-341`); external-form intake import has explicit file, row, column, and uncompressed-size limits (`oneforall/modules/ai_governance/import_rules.py`); the Vault confines ordinary download paths to configured roots; and outbound webhook requests require HTTPS, reject non-global DNS answers, avoid redirects, and bound response reads (`oneforall/core/outbound_http.py`). These are observations of selected paths, not a blanket security guarantee. The outbound HTTP module itself notes that DNS can change between validation and connection, so an egress firewall or proxy remains important.
